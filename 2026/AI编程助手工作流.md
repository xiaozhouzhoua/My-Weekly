# AI 编程助手工作流

## 概述

接上之前的 [Cursor 网页版记录](../2025/cursor.md)：AI 编程助手已经从「写个函数试试」
变成日常开发里的一环。真正拉开差距的，不是模型本身，而是**怎么把它组织进工作流**，
让它在可控范围内稳定产出，而不是制造「看起来对、跑起来炸」的代码。

## 选型参考

| 工具 | 形态 | 特点 |
|------|------|------|
| GitHub Copilot | IDE 插件 | 补全顺滑，和 GitHub 生态绑定 |
| Cursor | IDE/网页 | 改动大、项目级上下文强 |
| Claude Code / Codex CLI | 命令行 Agent | 适合自动化、批量任务 |
| 各类 Chat 助手 | 对话 | 答疑、评审、脚本快出 |

没有标准答案，按「补全 vs 大改 vs 批处理」三种场景组合着用最省事。

## 一条可复用的工作流

```
需求 → 拆解 → 写清约束 → 生成 → 审查 → 测试 → 提交
  │                                                        │
  └──────────── 每一步都让 AI 输出可验证的产物 ────────────────┘
```

1. **拆解**：把一个「大活」切成若干可独立验证的小任务，每步一个明确验收标准。
2. **约束**：说清语言版本、框架、依赖、风格、边界（哪些不能改）。
3. **生成**：让 AI 直接产出代码 + 测试，而不是先聊天。
4. **审查**：重点看**边界条件、并发、安全、错误处理**——这是模型最容易翻车的地方。
5. **测试**：跑测试、跑 lint、真实数据冒烟，不放过「看起来能跑」的代码。
6. **提交**：写清楚 commit message，diff 逐条过一遍再推。

## Prompt 要点

好的提示不是越长越好，而是**信息密度高**：

- 给上下文：相关文件、当前版本、报错信息、期望行为
- 给约束：明确的「必须 / 禁止」，例如「不要引入新依赖」「兼容 JDK 17」
- 给验收：可执行的验证方式，例如「用这个输入跑，期望这个输出」
- 让 AI 先复述理解：大任务先让它列出计划，你确认后再动手

## 与 Git 结合

让 AI 生成的东西始终**可回滚、可追溯**：

```bash
# 改动前先确认工作区干净，或另开分支
git checkout -b feat/ai-foo

# 每个小任务一个 commit，别攒成一个大黑盒
git add -A && git commit -m "feat: 新增 xxx"

# 评审时逐条看 diff，而不是整篇读
git diff HEAD~1
```

配合 `git bisect`、CI 门禁，出了问题能快速定位是哪一步引入的。

## 边界与风险

- **幻觉**：模型会编不存在的 API、错误的配置项，必须实测验证
- **安全**：别把密钥、内部代码、客户数据无脑贴进外部模型
- **许可证**：关注生成代码的来源与许可，避免照搬有版权争议的实现
- **审查责任**：最终对代码负责的是人，不是模型；AI 是「辅助」不是「托管」

## 小结

AI 编程助手的正确用法不是「替我写」，而是「把重复、机械的部分交给它，把方向、
边界和最终判断留给自己」。拆得越细、约束越清、验证越实，产出就越稳。
